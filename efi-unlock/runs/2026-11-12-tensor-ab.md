# A/B: tensor-MMA path locked vs unlocked (2026-11-12, guinea-pig llm2 GPU2)

Question: complete the 50HX lock profile — finding #3 of
`20260910-ab-stock-vs-efi.md` ("FFMA-FP32 and DP4A are clamped… FP16 half2
FMA and INT32 are NOT") never covered the tensor-MMA branch. Is the
FP16→FP32 accumulate path (`FMLA32`) clamped in the locked state like
FFMA/DP4A, and by how much? A clean 2.00× is a nice-to-have, **not** the
expectation — the goal is to name the ratio whatever it is.

## Method

- Tool: `tools/tensor_bench.cu` (ticket 01, gtuu-mining). Method ported from
  GPU-Tensor-Unlock-Universal @ 1d6a508 (GPL-2.0, `tensor_benchmark.py`,
  read-only static evaluation): runtime-randomized input fragments
  (anti-constant-folding — the mmapeak all-zero-fragment overcounting trap),
  finite non-zero IEEE-754 accumulator verification after **every** measured
  run, per-kernel timing loop. Build (sm_75 = fleet TU102):
  `nvcc -O3 -std=c++17 -arch=sm_75 -Xcompiler -Wall -o tensor_bench tools/tensor_bench.cu`
- Kernels: `FMLA16` (FP16→FP16 mma m16n8k8 baseline), `FMLA32` (FP16→FP32 mma
  m16n8k8 — the subject), `IMLA` (INT8→INT32 mma m8n8k16), `FFMA` (scalar
  FP32 CUDA-core control). BF16/TF32/FP8 absent on Turing: not measured.
- Guards (autotune-grade, per ticket Q9): idle-guard on the chosen card
  (util ≤5% over 10 s) before the run; single-GPU scoping via
  `CUDA_VISIBLE_DEVICES=<gpu2-index>` plain host run; power/cap/offset
  snapshot-restore with baseline-diff verification; teardown leaves the host
  byte-clean (governor restarted if touched, baseline caps verified,
  cmp50hx-boot flow unmodified).
- Guinea pig: **llm2 GPU2 (`0000:04:00.0`)**, baseline **170 W**.
- The unlock-skipped BEFORE boot is owner-gated (planned reboot of a
  serving-class host; schedule and confirm with the owner first). Rollback =
  normal boot (existing EFI README flow). Record exactly how the skipped
  state was entered and exited.
